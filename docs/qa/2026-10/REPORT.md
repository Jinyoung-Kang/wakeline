## 6. 출시 가능 여부
**판단: 조건부 출시 가능.**
- 근거(가능): 치명 결함 0. 높음 3건(데이터 손실 1 · 익명 요청으로 DB 고갈 2)과 보통 6건 · 낮음 20건을 근본 원인에서 고쳤고, 각 재현 시험이 고친 코드에서 통과하며 격리 스택에서
  실제 장애(api kill · DB 멈춤 · Redis 멈춤)와 부하로 다시 확인했다. 인증 · 인가 · CSRF · XSS · 헤더 · 비밀값 점검과 보안 게이트(gitleaks · trivy · 의존성 감사)에 걸린 것이 없다.
  기존 시험 전체와 표준 E2E 가 통과한다(§2). REST · WS 는 목표 안에서 2–3배 여유가 있다.
- 조건(남은 것 — 출시를 막지 않지만 결정이 필요):
  1. **QA-400 · NFR-03** — 2026-10-02 사용자 결정으로 잰 값에 맞게 다시 정했다: api 컨테이너 메모리 ≤ 768 MiB(컨테이너 한도 1 GiB 의 75 % — 잰 최대 750.5 MiB, OOM · 재시작 0,
     [ADR-031](../../adr/ADR-031-api-memory-target.md)). 힙 밖 약 290 MiB 를 줄이는 일은 필요해지면 따로.
  2. **QA-402 · QA-403 · 화면 CWV** — 2026-10-02 화면 성능 과제(PERF §15)로 개선: 실제 GPU 로 데스크톱 네 화면 모두 good, 소프트웨어 GL 의 `/` 모바일 LCP 7.6 → 2.7 s · TBT 7,449 → 871 ms.
     남은 모바일 TBT(배경지도를 그리면 442–474 ms) 등은 주인 결정('지금 상태로 둔다')으로 받아들였다.
- 배포 전 확인: 운영 배포 때 api 가 다시 떠야 QA-100 수정이 적용된다(그 전까지는 재시작마다 선박 위치 일부 손실 위험이 남는다).

4. 개선 제안 중 운영 영향이 큰 것: Redis 장애 중 요청 제한기가 Redis 무응답마다 3 s 기다림(공개 REST 가 장애 내내 3 s+ · `/status` 12 s), `/healthz` 가 DB 장애 · 기록 지연을 말하지 않음,
   기록기 백오프 상한 30 s, Redis 장애 중 AIS 위치가 최신값으로 합쳐지고 공백 기록이 없음(설계지만 문서에 없음).
5. 시험 공백(위험 경로): `OrderedWriter` 의 대기열 넘침(버림) · 종료 비우기, `StreamConsumer` 의 오류 · 회수 갈래, 수집기 `DbWriter` 의 종료 시 버림 · 예외 고리, 웹 커버리지 도구 없음.
6. 일관성: 같은 정수 파라미터의 범위 밖 처리(400 vs 자르기)와 모르는 필터 값의 처리를 맞추기, edge 가 만든 `/api` 오류를 problem+json 으로, Esc 닫기 · 토글 이름 · 맥락 없는 단추 이름.
