### 3.1 보안 게이트
- 첫 실행(`make security`, E2E 가 빌드한 브랜치 이미지): gitleaks 1,581 커밋 누출 0 · trivy collector · web · redis 통과 · npm audit · pip-audit 통과. **api(HIGH 2) · db(HIGH 11) · edge(HIGH 1) 실패** —
  모두 기반 이미지의 OS 패키지(curl CVE-2026-92392 · 8286 · 8927, expat CVE-2026-66046 · 76956 · 76957 · 77214 · 93990)로, 10-14 빌드 뒤 공개된 것이다. 코드 변경과 관계없다.
- 세 Dockerfile 은 빌드 때 OS 보안 갱신(`apt-get upgrade` · `apk upgrade`)을 받는데 빌드 캐시가 옛 층을 썼다. CLAUDE.md 절차대로 `docker compose … build --no-cache api db edge` 뒤
  다시 검사하니 **세 이미지 모두 통과**(고칠 수 있는 HIGH · CRITICAL 0).
- **최종**: 독립 검토 뒤 고친 것까지 합친 브랜치에서 E2E 가 다시 빌드한 이미지로 `make security` 를 다시 돌려 **전부 통과**(gitleaks 1,602 커밋 누출 0 · trivy 자체 5 · redis · npm audit · pip-audit).
- **배포할 때 주의**: main 의 지금 이미지 · AWS EC2 의 빌드 캐시도 같은 옛 층을 가질 수 있다 — 다음 배포는 api · db · edge(AWS 는 api)를 `--no-cache` 로 빌드하기를 권한다.
- 보고만 하는 도구 이미지 k6(`make bench`, 배포 안 함)는 고칠 수 있는 HIGH 6(Alpine libcrypto3 2 · k6 바이너리의 Go net/http · crypto/tls 4)이 있다 — Makefile `K6_IMAGE` 를 올릴 때 함께(이번 범위 밖).

### 3.2 성능
측정된 병목 발견이 없어 성능 변경은 하지 않았다. 바뀐 수치: 첫 화면 JS(위 표). IM-03 은 장애 중 실패한 발행마다 하던 전체 사본(10만 건에 순간 +47 MiB · 루프 ≈ 0.2 s — 리뷰어 측정)을 없앴다(평소 경로 비용 변화 없음). IM-07 은 판정마다 스코프 4개의 시각 최댓값 하나를 더 구한다(병합 뷰는 그대로 — 엔진 전용 뷰는 측정 없이 하지 않았다).

## 6. 남은 위험과 다음 단계
- **판정 엔진(IM-07)**: 병합 뷰는 여전히 벽시계 — 따라잡기가 focus 60 s · hot 90 s(장애 10분 넘으면 global 600 s)보다 길면 그 피드로만 보이는 기체는 부재로 셀 수 있다. 엔진 전용 뷰는 성능 측정 뒤.
- **벽시계 역행(IM-08)**: SIGMET · 특보 **이력** 저장의 중복 막기(lastSetAt)와 `/healthz` 의 'no_region_snapshot'(공개 사유 — 이제 길어야 관심 지역 한 주기)은 같은 원인이 남은 곳.
  실제 환경에서 계단 보정이 얼마나 생기는지는 재지 않았다.
- **독립 검토에서 기록만 한 것**: 항공기 DB 보충 검색(SQL)이 정확 일치를 앞에 두지 않음(R4 — 원래 있던 빈틈, 실행 계획 영향을 재야 함) · 자격 확인 결함 경로의 ERROR 줄에 request_id 가 없을 수 있음(R5 — 미검증) · 선택 항공기 · 선박 DB 항적도 503 + Retry-After 뒤 다시 받지 않음(R12 — 지금은 '기록 조회 실패'를 적는다).
- **역행 직후 체류**: 시계가 뒤로 간 직후 LEFT 가 나면 `left_at` 이 `entered_at` 보다 이를 수 있다(음수 체류가 통계에 섞일 수 있다 — ADR-040).
- **같은 부류로 남긴 것**(제안): 웹이 항공기 검색 · `/watch` 의 `meta.db_unavailable` 을 읽지 않음, 운영 컨트롤러의 'redis unavailable' catch 가 원인을 남기지 않음, 교통량 발행 실패 WARN 이 틱마다, 알림 해결 메모 본문의 `strip()`, 웹 `topAboveFromRaw` 죽은 길(수집기가 같은 값 ABV 를 하한으로 내므로 실제 자료에서 쓰이지 않음), ErrorScreen · 청크 확인이 `/maplibre/` 경로를 보지 않음.
- **다음 단계**: Q1 · Q2 · Q4 결정 → main 병합 · push(사용자) → 배포(로컬은 `make up` — 그 전에 api · db · edge 를 `--no-cache` 로 빌드, AWS 는 ADR-039 명령으로 api · collector · web 을 다시 빌드(api 는 `--no-cache` 권장) — 마이그레이션 변화 없음) → 이어지는 QA.
