# ADR-024 운영자의 '해결' 표시: 지우지 않고 upto 까지 가린다

**상태** 채택 · 2026-09-29 · 계약 v5 §G14 · 사용자 요청 "해결 완료된 [운영/로그] 메뉴에 있는 error 는 지우는 기능"

## 배경
[운영](공급자 `last_error` · 수집 실행 요약의 error 행)과 [로그](fp 묶음)는 이미 해결한 오류도 보존 기간 내내 그대로 보인다. 운영자는 새 오류와 끝난 오류를
구분하지 못하고, 매번 같은 오류를 다시 읽는다. 그렇다고 오류를 실제로 지우면 증거가 사라진다 — 원인 분석 · 재발 확인 · 감사가 그 기록에 기댄다.

## 결정
- **지우지 않고 가린다.** 운영자는 `(kind, key, upto)` 를 적는다: kind = `log_group`(key = 로그 지문 fp) | `provider_error`(key = 공급자 이름).
  그 key 의 upto 이하에 난 오류가 "해결됨" 이고, 조회(`/ops/logs` · `/ops/logs/groups` · `/ops/runs` 요약)는 기본으로 그것을 뺀 뒤 뺀 수를 알린다
  (`hidden_resolved` · `hidden_resolved_errors`). `resolved=show` 로 언제든 다시 본다. 로그 스트림 · `ingest_run` · 공급자 해시는 그대로다.
- **upto 는 범위의 끝이다(상태 플래그가 아니다).** upto 뒤의 새 발생은 해결되지 않은 것으로 다시 보인다 — "해결" 이 재발을 숨기지 않는다.
  같은 key 에 활성 해결이 여럿이면 upto 가 가장 늦은 것이 유효하다(가장 최근 해결을 되돌리면 앞선 해결의 범위로 돌아간다 — 되돌림이 예상 밖으로 많은 것을 되살리지 않는다).
- **원본은 DB 표(V13 `ops_resolution`)**, 감사(`RESOLVE` · `UNRESOLVE`)와 한 트랜잭션. 되돌림은 행을 지우지 않고 `revoked_at` · `revoked_by` 를 채운다.
  api 계정은 그 두 열만 고칠 수 있다(열 단위 GRANT) — 누가 언제 무엇을 어디까지 해결했는지는 한 번 적으면 바뀌지 않는다.
- **읽기는 api 가 5 s 이하 캐시**하고 쓰기 뒤 바로 버린다. 로그 조회는 Redis 만 읽는 경로라 요청마다 DB 를 더 부르지 않고, DB 장애 중에도 된다:
  읽지 못하면 마지막으로 읽은 해결로 가리고(`resolution_state: stale`), 한 번도 읽지 못했으면 아무것도 가리지 않는다(`unavailable`). 어느 쪽이든 응답이 말한다.
  다시 읽기는 한 번에 하나이고 다른 요청은 그동안 지난 값을 받는다 — 느린 DB(연결 대기 5 s + 문장 3 s)를 기다리는 것은 30 s 에 한 요청뿐이다.
- 실행 요약은 요약 자체가 DB 조회라 같은 문장에서 해결을 읽는다(캐시 없음). 공급자 오류는 status `'error'` 실행만이다 — collector 가 `last_error` 를 쓰는 실행과 같다.
  실행의 발생 시각은 **실패를 기록한 시각(`finished_at`)** 이다 — 공급자 해시의 `last_error_at` 과 같은 순간이라 두 화면이 한 실패에 같은 답을 한다. 시작 시각으로
  보면 해결 순간에 진행 중이던 실행(단계마다 읽기 8 s · 재시도)이 upto 뒤에 실패해도 가려진다. `finished_at` 이 없으면 모르는 것이라 가리지 않는다.

## 대안과 기각 이유
- 로그 항목 삭제(`XDEL`) · 실행 기록 `DELETE`: 증거가 사라진다. 사용자가 되돌릴 수 없고, 같은 fp 가 다시 나도 전에 있었는지 알 수 없다. api 의 `ingest_run` 권한도
  보존 정리용 DELETE 뿐이라 화면 조작으로 지우게 하는 것은 권한 모델에 어긋난다.
- 항목 id 마다 '확인' 표시: 로그는 최대 4,200건 · 같은 fp 가 수십 번 — 하나씩 누르게 된다. fp · 공급자 단위 + upto 가 운영자가 실제로 판단하는 단위다.
- 기한이 지나면 풀리는 음소거(TTL): 원인이 남아 있어도 조용히 다시 나타나거나, 반대로 새 오류가 기한 동안 숨는다. upto 는 "그때까지 본 것" 이라는 사실만 적는다.
- 한 key 에 활성 해결 하나만(새 해결이 이전 것을 되돌림): 가장 최근 해결을 되돌리면 그 key 의 모든 오류가 되살아난다 — 운영자가 기대하는 "방금 한 것만 취소" 와 다르다.
- Redis 에 저장: 로그와 같은 곳이라 가깝지만 감사와 한 트랜잭션으로 묶을 수 없고, Redis 볼륨을 잃으면 해결이 조용히 사라진다(ADR-019 의 공급자 스위치와 같은 이유).

## 결과
- 새 표 하나(작다 — 운영자의 클릭 수만큼). 로그 조회는 fp 마다 해시 조회 한 번을 더한다(훑기 4,200건 상한 그대로).
- 운영 · 로그 화면은 `hidden_resolved` 와 `resolution_state` 를 보여야 한다 — 가린 것이 있다는 사실을 숨기지 않는다.
- 되돌리기: V13 머리 주석의 SQL(`DROP TABLE ops_resolution` + 이력 행) + 코드 되돌리기 — 가림이 없어져 모든 오류가 다시 보이고 감사 행은 남는다.
