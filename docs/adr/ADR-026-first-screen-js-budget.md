# ADR-026 첫 화면 JS 예산: 400 KB 대신 550,000 B(gzip 본문) — 지도 라이브러리와 Next · React 가 바닥이다

**상태** 채택 · 2026-09-30 · NFR-04 의 '첫 화면 JS ≤ 400 KB gzip' 개정(같은 NFR 의 30 fps · LCP 목표는 그대로) · 사용자 위임 — "첫 화면 JS 크기 목표 … 너의
권장(추천) 방안대로 처리해" · 측정 [PERF §10](../PERF.md)

## 맥락
- NFR-04 목표는 `/` 첫 화면 JS 400 KB(gzip)다. 리뷰 v1 부터 한 번도 맞추지 못했다(Lighthouse 스크립트 transferSize: 613.6 → 497.7 → 526.3 → 520.6 KiB,
  PERF §7 · §8). 목표를 다시 정할지는 사용자 결정으로 남아 있었고, 사용자가 권장안으로 처리하라고 맡겼다.
- 측정이 스택 + Lighthouse 에 기대어 로컬에서 되풀이하기 어려웠고, 무엇을 세는지(응답 머리 · 워커)가 적혀 있지 않았다.
- 이 결정의 기준 커밋(`83b4ab2`)을 새 도구로 잰 값(PERF §10 — 웹 이미지의 Node 로 압축): 19개 파일 · **556,719 B**. 그 가운데
  - MapLibre GL 6.11.2 세 파일(메인 · 공용 · 워커) **304,573 B**
  - 파일 전체가 Next · React · Turbopack 실행 코드인 청크 다섯 **133,532 B**
  - → 이 둘만 **438,105 B**: 우리 코드가 0 B 여도 400 KB(400,000 B · 400 KiB 어느 쪽으로 읽어도)를 넘는다.

## 결정
1. **단위 = gzip 본문 바이트(응답 머리 제외), 웹 이미지의 Node 가 압축한 값**. 웹 서버(Next standalone `server.js`)가 내장 compression(gzip · zlib 수준 6 ·
   1 KiB 미만 무압축)으로 압축하고, edge(nginx `gzip on`)는 이미 `Content-Encoding` 이 붙은 응답을 다시 압축하지 않는다 → 배포 스택이 보내는 본문은 웹 이미지
   (Dockerfile 실행 단계의 다이제스트 고정 `node:24-alpine` — Node 24.21.0 · 내장 zlib 1.3.2.1-motley-8002e91)가 만든 gzip 이다. gzip 결과는 zlib 구현마다
   다르다: 같은 빌드를 macOS Homebrew Node 24.3.0(시스템 zlib 1.2.12)으로 압축하면 0.41–0.44 % 작다(PERF §10 '압축기별 값'). 그래서 CI 의 검사는 웹 이미지 안에서
   돌고(`check:first-js -- --in-image`), 모든 표 머리에 압축기(Node · zlib · 플랫폼/아키텍처)를 적는다. 배포 스택(`83b4ab2` 빌드)을 브라우저 측정으로 잰 19개 파일 ·
   556,719 B 는 같은 빌드를 웹 이미지의 Node 로 계산한 값과 파일마다 같았다. 응답 머리는 경로마다 다르므로(edge 가 보안 헤더 · Cache-Control 을 붙인다) 뺀다.
   옛 Lighthouse 값(머리 포함)과는 단위가 다르다 — 그때 커밋 `b9ebfb4` 를 웹 이미지의 Node 로 계산하면 530,798 B, Lighthouse 520.6 KiB ≈ 533,094 B
   (남는 약 2.3 KB 가 무엇인지는 나눠 재지 않았다).
2. **무엇을 세는가**: `/` 를 빈 캐시로 열 때 받는 스크립트 전부 — Next 가 `/` 의 첫 로드로 적은 청크(`.next/diagnostics/route-bundle-stats.json`),
   `/` 의 `next/dynamic` 청크(지도 컴포넌트 — `react-loadable-manifest.json`), `public/maplibre/<버전>/` 세 파일, 지도가 띄우는 보간 워커. 같은 주소는 한 번
   (워커가 공용 청크를 다시 import 하는 것은 캐시). **첫 화면의 끝**은 지도가 처음 다 그려진 때(MapLibre 'load')다 — 상황판은 그 뒤 브라우저가 한가할 때
   표시(`performance.mark('wakeline:after-first-screen')`)를 남기고 조각을 미리 받는다. 표시 뒤의 요청과, 그 전이라도 클릭 · 탭 · 펼치기 · 검색 뒤에만 받는 조각은
   세지 않는다(브라우저 측정은 표시 앞뒤를 가르고, 앞의 파일 목록이 빌드 결과 목록과 같은지 본다).
3. **첫 화면에서 뺀 것**(낮은 위험 — 동작 · 접근성 · SSR 그대로): 항공기 · 선박 · SIGMET · 공항 카드와 목록, 알림 근거, 기상청 레이더 범례·정합 패널, 통합 검색의
   선박 표를 처음 쓸 때 받는다(`components/DashboardParts.tsx` · `LazyPart.tsx`). 받는 동안 진행 표시 규칙(글자 곧바로 · 막대 · 자리 표시는 180 ms 뒤),
   못 받으면 까닭 · 다시 시도 · 시스템 로그 보고. 검색창에 초점이 오면 선박 표를 미리 받는다. **556,719 → 541,820 B(−14,899 B, 웹 이미지의 Node)**.
   카드 · 표에서만 쓰는 선박 함수와 문구를 `lib/ship-card.ts` 로 옮겨(조각만 싣는다) **→ 539,966 B**(아래 두 보완 +1,791 B 포함, PERF §10 '리뷰 뒤').
   - **첫 화면 뒤 미리 받기**: 지도가 처음 다 그려지고 한가하면(requestIdleCallback, 최대 5 s — 선택값) 조각 9개(격리 스택 49,758 B)를 받아 둔다 — 첫 클릭에 기다리지 않고,
     오래 열어 둔 상황판이 새 배포 뒤에도 카드 · 목록을 연다(청크 이름은 내용 해시이고 새 웹 이미지는 제 청크만 싣는다 — 옛 주소는 404).
   - **새 배포 뒤 못 받은 조각**: 서버에 그 청크가 있는지 HEAD 로 한 번 확인해(추측하지 않는다) 404 · 410 이면 '다시 시도' 대신 '페이지 새로고침'과 까닭을,
     있으면 '다시 시도'를 보이고, 다시 시도가 또 실패하면 둘 다 보인다. 확인 결과를 붙여 시스템 로그에 보고한다. 다시 시도 뒤 초점은 불러온 조각(또는 새 오류의 첫 단추)으로.
     못 받은 뒤 다른 경로(미리 받기 · 다른 자리의 다시 시도)로 받으면 누르지 않아도 오류 자리가 조각으로 바뀐다(통합 마무리 리뷰 2026-09-30 — `useLoaded()` 구독).
     조각이 없는 동안 그 안의 요소를 가리키지 않는다: 통합 검색 콤보박스는 선박 표 조각을 받은 뒤에만 선박 줄을 키보드 이동 · Enter · aria-controls · aria-activedescendant 에 넣는다.
   - `next/dynamic` 이 아니라 `React.lazy` 로 한다: 빌드 결과 검사는 `/` 의 `next/dynamic` 을 '첫 그리기에 받는 JS' 로 센다(지도만 — 시험이 본다).
   - 남긴 것과 까닭: 범례(1600 px 이상에서는 처음부터 펼쳐진다 — lib/prefs), 상태 바 · 알림 목록 · 레이더 줄 · 레이어 단추(처음부터 보인다),
     WS 검증기(첫 메시지부터 쓴다 — 선택 항목의 노선 · 입출항 해석도 검증기가 부른다), 통합 검색 입력(머리글에 늘 있다).
   - 나누지 않은 후보(잰 값 — 이 브랜치 사본에서 그 코드를 없앤 판, 웹 이미지의 Node, 기준 543,611 B): 상태 바 '상세' 표 −2,354 B(나눴을 때의 최대) — 팝오버의
     초점 · Esc · 바깥 누르기 처리가 패널 ref 에 묶여 불러오는 동안의 자리와 얽히므로 이 크기에는 나누지 않는다. 검색 결과 화면 −328 B(청크 묶음이 바뀌어 거의 줄지 않는다).
     ops · 설명서 전용 코드는 `/` 첫 그리기 그래프에 없다(59개 모듈 가운데 그 경로의 둘 — 오류 화면 · 요청 id 표시 — 은 `/` 가 쓴다).
4. **예산 = 550,000 B(537.1 KiB)** — **선택값**(잰 값이 아니다): 처음 정할 때 호스트 zlib 으로 잰 539,430 B 에 약 2 % 를 더했다. 기준 압축기(웹 이미지의 Node)로
   지금(`40e5582`) 539,966 B · 여유 10,034 B(약 1.8 %)다. PERF §8 측정(`b9ebfb4`) 뒤 기준 커밋까지 커밋들이 첫 화면에 25,921 B 를 더했다(PERF §10) — 여유는 그런 흐름이
   다시 쌓이면 넘도록 작게 잡았다. 400 KB 는 지도 라이브러리를 첫 화면에서 빼야만 닿는다.
   **바이트 여유가 잡는 것과 못 잡는 것**(통합 마무리 리뷰 2026-09-30 이 이 브랜치 사본에서 잰 값 — 호스트 zlib, 기준 538,481 B): 나중에 받게 한 일을 대부분 되돌리면
   넘는다(SidePanel · AlertPanel · RadarTimeline · AircraftSearch 의 조각을 모두 정적으로 되돌린 판 560,646 B — 검사 실패). 그러나 **조각 하나**를 첫 화면으로 되돌리는 것은
   가장 큰 것도 여유 안이다(SidePanel 이 항공기 카드를 정적으로 부르게 한 판 — 알림 근거도 함께 실린다 — 542,912 B, +4,431 B, 웹 이미지 zlib 은 약 0.43 % 커도 예산 안).
   그것은 바이트 검사가 아니라 `tests/first-screen-lazy.test.ts`(CI web job 의 Vitest — 그 판에서 두 건 실패: 항공기 카드 · 알림 근거가 첫 화면 그래프에 있음)가 잡는다.
   즉 바이트 여유는 여유(지금 약 9 KB)보다 큰 새 정적 코드와 조각 작업의 대부분을 되돌리는 것을, 조각 목록 시험은 조각 하나하나를 지킨다.
5. **지키는 방법**: CI 의 web job 이 운영 빌드 뒤 `npm run check:first-js -- --in-image`(빌드 결과만으로 계산 — 스택 · 브라우저 없음, 웹 이미지의 Node 로,
   넘으면 실패, 빌드 결과를 읽지 못하거나 docker 가 이미지를 받지 못해도 실패)를 돌린다(`apps/web/tests/first-screen-js.test.ts` 가 순서와 인자를 본다).
   배포 스택은 `npm run measure:first-js -- http://localhost:8700`(Playwright — 페이지만 연다), 로컬은 `-- --serve 879x`(운영 빌드를 127.0.0.1 에 — 호스트의 Node 로
   압축하므로 바이트가 기준과 조금 다르다). 두 도구는 같은 압축기일 때 같은 파일 · 같은 바이트를 냈다(로컬 standalone 서버 554,299 · 539,430 · 537,669 B,
   배포 스택 `83b4ab2` 556,719 B, 이 브랜치를 올린 버리는 격리 스택 539,966 B).
   CI 러너(amd64)에서의 값은 아직 없다 — 첫 CI 실행 로그의 합계를 PERF §10 에 적는다.
   **이 검사가 보는 것과 못 보는 것**: 빌드 결과의 첫 로드 목록 · `/` 의 next/dynamic · MapLibre 배포본 · 보간 워커를 센다. import() · React.lazy 로 받는
   조각은 세지 않는다 — 그래서 (a) 첫 그리기 그래프의 import() 는 세 곳(조각 목록 · 지도 next/dynamic · MapLibre)에만 있어야 하고, 조각은 '언제 처음
   보이는가'가 적힌 목록과 정확히 같아야 한다(`tests/first-screen-lazy.test.ts`), (b) CI 의 web job 이 운영 빌드를 127.0.0.1:8790 에 띄워 Chromium 으로 두 창
   크기(1350×940 · 범례가 처음부터 펼쳐지는 1700×1000)에서 첫 화면에 받는 스크립트가 빌드 결과 목록과 같은지 본다(`measure:first-js -- --serve 8790` — 다르면 실패).
   리뷰의 실험(넓은 창에서 처음부터 보이는 범례를 조각으로 옮김 — 빌드 결과 검사는 536,541 B '예산 안')을 (a)는 import() 자리로, (b)는 1700 px 창에서
   빌드 목록에 없는 청크 하나로 잡았다. 조각의 까닭이 맞는지(정말 상호작용 뒤에만 보이는지)는 사람이 목록을 읽어 판단한다 — 시험은 까닭이 적혔는지만 본다.
6. **예산을 바꾸는 절차**: `check:first-js` 의 표로 무엇이 늘었는지 적고, 상호작용 뒤로 미룰 수 없는 까닭을 쓰고, `FIRST_SCREEN_JS_BUDGET` · PERF §10 ·
   이 ADR 을 한 커밋에서 바꾼다(`tests/first-screen-js.test.ts` 가 세 곳의 숫자가 같은지, 예산이 바닥보다 큰지 본다).

## 대안
- **400 KB 유지 · 지도를 첫 화면 뒤로**: 상황판의 본체가 지도라 첫 화면이 빈 칸이 된다 — 거절.
- **다른 지도 라이브러리**: 항공기 약 1만 대 · 선박 약 3만 척(PERF §1)을 WebGL 로 그리는 MapLibre 를 바꾸는 일은 이 결정의 범위 밖이다.
- **brotli**(참고 — 잰 값, 도입 결정 아님): `40e5582` 의 같은 18개 파일을 brotli 품질 11(미리 압축)로 만들면 456,106 B · 품질 6(요청 때 압축)은 503,727 B
  (Node 내장 brotli 1.2.0), 바닥(MapLibre 3 + Next 순수 청크 4)은 363,713 B. brotli 로도 지금 코드는 400 KB 를 넘는다. 도입하려면 edge 모듈 또는 미리 압축한 파일 제공이 필요하고
  단위 · 예산을 다시 정한다.
- **Lighthouse transferSize 를 계속 단위로**: 머리가 경로마다 달라 로컬 · CI 에서 같은 값을 낼 수 없다 — 버렸다(옛 값은 PERF §7 · §8 에 그대로 둔다).

## 결과
- NFR-04 의 JS 항목은 "첫 화면 JS ≤ 550,000 B(gzip 본문, 응답 머리 제외, 웹 이미지의 Node 로 압축)" 로 읽는다. `40e5582` 539,966 B · 세 레인(ui · collector · js) 통합 뒤 540,774 B(여유 9,226 B — PERF §10 '세 레인 통합 뒤') · 통합 마무리 리뷰의 수정 뒤 540,955 B(여유 9,045 B) — 충족.
- 정적으로 첫 화면에 실리는 새 코드가 여유(`40e5582` 10,034 B · 통합 마무리 뒤 9,045 B)를 넘으면 CI 의 예산 검사가 실패한다. 그보다 작은 되돌림(조각 하나를 정적으로)은 위 4 대로 조각 목록 시험이 잡는다. 조각(import())으로 첫 그리기에 실리는 코드는 그 검사가 세지 않고,
  대신 위 5 의 (a) · (b)가 막는다(조각 목록 밖의 import() · 브라우저 첫 화면 목록 ≠ 빌드 목록). 줄이려면 상호작용 뒤에만 보이는 화면을 조각으로 옮기고 까닭을 적거나,
  위 절차로 예산을 바꾼다.
- 나중에 받는 조각은 첫 화면 뒤 한가할 때 미리 받고, 그 전에 열면 그때 받는다(로컬 standalone 서버에서 Chromium 으로 확인: 늦게 오면 진행 표시, 끊기면
  'HTTP 200 — 다시 시도'로 되살아나고 초점은 불러온 목록으로, 처음 받은 것 밖의 청크를 404 로 답하면 'HTTP 404 — 새 판이 배포되면' 과 '페이지 새로고침' — 그때의 단추 글자는
  '페이지 새로 고침' 이었고 통합 마무리 리뷰에서 사용자 표기 '새로고침'(VERIFICATION #71)으로 맞췄다).
