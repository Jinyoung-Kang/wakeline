# ADR-026 첫 화면 JS 예산: 400 KB 대신 550,000 B(gzip 본문) — 지도 라이브러리와 Next · React 가 바닥이다

**상태** 채택 · 2026-09-30 · NFR-04 의 '첫 화면 JS ≤ 400 KB gzip' 개정(같은 NFR 의 30 fps · LCP 목표는 그대로) · 사용자 위임 — "첫 화면 JS 크기 목표 … 너의
권장(추천) 방안대로 처리해" · 측정 [PERF §10](../PERF.md)

## 맥락
- NFR-04 목표는 `/` 첫 화면 JS 400 KB(gzip)다. 리뷰 v1 부터 한 번도 맞추지 못했다(Lighthouse 스크립트 transferSize: 613.6 → 497.7 → 526.3 → 520.6 KiB,
  PERF §7 · §8). 목표를 다시 정할지는 사용자 결정으로 남아 있었고, 사용자가 권장안으로 처리하라고 맡겼다.
- 측정이 스택 + Lighthouse 에 기대어 로컬에서 되풀이하기 어려웠고, 무엇을 세는지(응답 머리 · 워커)가 적혀 있지 않았다.
- 이 브랜치 시작(`83b4ab2`)을 새 도구로 잰 값(PERF §10): 19개 파일 · **554,299 B**. 그 가운데
  - MapLibre GL 6.11.2 세 파일(메인 · 공용 · 워커) **303,421 B**
  - 파일 전체가 Next · React · Turbopack 실행 코드인 청크 다섯 **133,462 B**
  - → 이 둘만 **436,883 B**: 우리 코드가 0 B 여도 400 KB(400,000 B · 400 KiB 어느 쪽으로 읽어도)를 넘는다.

## 결정
1. **단위 = gzip 본문 바이트**(응답 머리 제외). 웹 서버(Next standalone `server.js`)가 내장 compression(gzip · zlib 수준 6 · 1 KiB 미만 무압축)으로 압축하고,
   edge(nginx `gzip on`)는 이미 `Content-Encoding` 이 붙은 응답을 다시 압축하지 않는다 → 배포 스택과 로컬 standalone 서버의 본문 바이트가 같다. 응답 머리는
   경로마다 다르므로(edge 가 보안 헤더 · Cache-Control 을 붙인다) 뺀다. 옛 Lighthouse 값(머리 포함)과는 단위가 다르다 — 그때 커밋 `b9ebfb4` 를 새 도구로
   계산하면 528,597 B, Lighthouse 520.6 KiB = 533,094 B(차 4,497 B ≈ 머리 17건, 추정).
2. **무엇을 세는가**: `/` 를 빈 캐시로 열 때 받는 스크립트 전부 — Next 가 `/` 의 첫 로드로 적은 청크(`.next/diagnostics/route-bundle-stats.json`),
   `/` 의 `next/dynamic` 청크(지도 컴포넌트 — `react-loadable-manifest.json`), `public/maplibre/<버전>/` 세 파일, 지도가 띄우는 보간 워커. 같은 주소는 한 번
   (워커가 공용 청크를 다시 import 하는 것은 캐시). 클릭 · 탭 · 펼치기 · 검색 뒤에만 받는 조각은 세지 않는다 — 받는 시점이 첫 화면 뒤다.
3. **첫 화면에서 뺀 것**(낮은 위험 — 동작 · 접근성 · SSR 그대로): 항공기 · 선박 · SIGMET · 공항 카드와 목록, 알림 근거, 기상청 레이더 범례·정합 패널, 통합 검색의
   선박 표를 처음 쓸 때 받는다(`components/DashboardParts.tsx` · `LazyPart.tsx`). 받는 동안 진행 표시 규칙(글자 곧바로 · 막대 · 자리 표시는 180 ms 뒤),
   못 받으면 까닭 · 다시 시도 · 시스템 로그 보고. 검색창에 초점이 오면 선박 표를 미리 받는다. **554,299 → 539,430 B(−14,869 B)**.
   - `next/dynamic` 이 아니라 `React.lazy` 로 한다: 빌드 결과 검사는 `/` 의 `next/dynamic` 을 '첫 그리기에 받는 JS' 로 센다(지도만 — 시험이 본다).
   - 남긴 것과 까닭: 범례(1600 px 이상에서는 처음부터 펼쳐진다 — lib/prefs), 상태 바 · 알림 목록 · 레이더 줄 · 레이어 단추(처음부터 보인다),
     WS 검증기(첫 메시지부터 쓴다 — 선택 항목의 노선 · 입출항 해석도 검증기가 부른다), 통합 검색 입력(머리글에 늘 있다).
   - 나누지 않은 후보(크기는 따로 재지 않았다): `lib/ships.ts` 의 카드 전용 부분(정적 보고 문구 · ETA · 목적지 줄 — 모듈을 나눠야 한다),
     검색 결과 화면(`SearchResultsView`), 상태 바 '상세' 표.
4. **예산 = 550,000 B(537.1 KiB)** — **선택값**(잰 값이 아니다): 결정 때 잰 539,430 B + 여유 10,570 B(약 2 %). 여유는 작은 조각 몇 개가 첫 화면에 새로 실리면
   넘도록 작게 잡았다 — PERF §8 측정(`b9ebfb4`) 뒤 이 브랜치 시작까지 커밋들이 첫 화면에 25,702 B 를 더했다(PERF §10). 400 KB 는 지도 라이브러리를 첫 화면에서 빼야만 닿는다.
5. **지키는 방법**: CI 의 web job 이 운영 빌드 뒤 `npm run check:first-js`(빌드 결과만으로 계산 — 스택 · 브라우저 없음, 넘으면 실패, 빌드 결과를 읽지 못해도
   실패)를 돌린다(`apps/web/tests/first-screen-js.test.ts` 가 순서를 본다). 배포 스택은 `npm run measure:first-js -- http://localhost:8700`(Playwright — 페이지만 연다),
   로컬은 `-- --serve 879x`(운영 빌드를 127.0.0.1 에). 두 도구는 이 브랜치에서 두 번(554,299 · 539,430 B — 로컬 standalone 서버) 같은 파일 · 같은 바이트를 냈다.
   배포 스택에서는 이 결정 때 재지 않았다(결정 1 의 까닭으로 본문 바이트가 같아야 한다 — 배포 뒤 한 번 재어 PERF 에 적는다).
6. **예산을 바꾸는 절차**: `check:first-js` 의 표로 무엇이 늘었는지 적고, 상호작용 뒤로 미룰 수 없는 까닭을 쓰고, `FIRST_SCREEN_JS_BUDGET` · PERF §10 ·
   이 ADR 을 한 커밋에서 바꾼다(`tests/first-screen-js.test.ts` 가 세 곳의 숫자가 같은지, 예산이 바닥보다 큰지 본다).

## 대안
- **400 KB 유지 · 지도를 첫 화면 뒤로**: 상황판의 본체가 지도라 첫 화면이 빈 칸이 된다 — 거절.
- **다른 지도 라이브러리**: 항공기 약 1만 대 · 선박 약 3만 척(PERF §1)을 WebGL 로 그리는 MapLibre 를 바꾸는 일은 이 결정의 범위 밖이다.
- **brotli**(참고 — 잰 값, 도입 결정 아님): 같은 18개 파일을 brotli 품질 11(미리 압축)로 만들면 457,695 B · 품질 6(요청 때 압축)은 504,802 B,
  바닥(MapLibre 3 + Next 순수 청크 4)은 363,713 B. brotli 로도 지금 코드는 400 KB 를 넘는다. 도입하려면 edge 모듈 또는 미리 압축한 파일 제공이 필요하고
  단위 · 예산을 다시 정한다.
- **Lighthouse transferSize 를 계속 단위로**: 머리가 경로마다 달라 로컬 · CI 에서 같은 값을 낼 수 없다 — 버렸다(옛 값은 PERF §7 · §8 에 그대로 둔다).

## 결과
- NFR-04 의 JS 항목은 "첫 화면 JS ≤ 550,000 B(gzip 본문, 응답 머리 제외)" 로 읽는다. 지금 539,430 B — 충족.
- 새 첫 화면 코드가 여유(10,570 B)를 넘으면 CI 가 실패한다 — 조각을 나중에 받게 하거나 위 절차로 예산을 바꾼다.
- 나중에 받는 조각은 처음 열 때 한 번 청크를 받는다(로컬 standalone 서버에서 각 탭 · 패널이 처음 열 때 청크 하나씩 받고, 늦게 오면 진행 표시,
  끊기면 오류 · 다시 시도로 되살아나는 것을 Chromium 으로 확인했다).
