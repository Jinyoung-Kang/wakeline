# ADR-013 수요 기반 정밀 추적: 뷰포트 핫 리전 + 선택 항공기 집중 추적

**상태** 채택 · 2026-09-28

## 배경
전세계 스냅샷(OpenSky)은 크레딧 한도 때문에 120초 간격이라 항적이 꺾인 선으로 보인다. 무료 공급자의 호출량은 한정돼 있으므로, 사람이 실제로 보고 있는 곳에만 호출을 더 쓴다.

## 확인한 사실(2026-09-28 실측·문서)
- adsb.fi opendata: `/v2/icao/{hex[,hex...]}` 로 여러 hex 를 한 요청에 조회(5대 0.39 s 실측), `/v3/lat/{lat}/lon/{lon}/dist/{nm}` (≤ 250 NM). 공개 엔드포인트는 "1 request per second", 개인·비상업, 출처 표기(README 인용).
- adsb.lol: 같은 IP 에서 관심 지역 10 s 수집 중 `/v2/hex` 조회가 429 — 정밀 추적을 얹을 여유가 없다.

## 결정
1. **수요는 서버가 세션에서 만든다.** 브라우저는 임의 지역·주기를 요청하지 못한다. api 가 각 WS 세션의 뷰포트·선택을 보고 수요를 계산해 Redis 임대(lease)로 기록한다.
   - 선택 항공기가 있으면 그 세션은 **집중 추적(focus)** 수요만 낸다(핫 리전 수요 없음).
   - 선택이 없고 줌 ≥ 7 이며 화면 중심이 고정 관심 지역(한반도 원) 밖이면 **핫 리전(hot)** 수요: 중심을 0.5° 격자로 맞추고 반경 = min(250, 화면 반대각선) NM 을 50 NM 단위로 올림. 같은 셀은 세션끼리 공유한다.
   - 임대는 60 s 뒤 만료되고 세션이 살아 있는 동안 10 s 마다 갱신된다(점수 = api 시계의 만료 epoch ms, 키 만료 = api 시계로 잰 남은 시간(PEXPIRE) — Redis 시계와의 차이만큼 키가 60 s 를 넘겨 살지 않게). 창을 닫거나 연결이 끊기면 최대 60 s 안에 호출이 멈춘다. 한 세션의 연속 집중 추적은 30분 상한(비용 상한) — 넘으면 화면이 알리고 다시 선택하면 이어진다.
2. **수집기는 임대만 읽어 조회한다.** focus: 활성 hex 전부를 5 s 마다 adsb.fi 묶음 요청 1회(최대 50 hex/요청). hot: 활성 셀마다 30 s 간격 `/v3/lat/lon/dist`.
3. **호출 상한은 수집기 한 곳에서.** 호스트별 토큰 버킷(adsb.fi 0.8 req/s, 공식 1 req/s 의 80 %)과 수집기 전체 상한, 하루 예산. 여유가 없으면 우선순위(고정 관심 지역 > focus > hot)대로 쓰고, hot 은 주기를 늘리고(30→60→120 s) 셀 수를 줄인다(세션 수 순). 상태(active·throttled·not_found)는 화면에 그대로 보인다 — 약속한 주기를 못 지키면 그렇다고 표시한다.
4. **병합은 신선도 우선.** 같은 hex 가 여러 출처(고정 지역·hot·focus·전세계)에 있으면 seen_at 이 가장 최근인 관측을 쓴다(출처 고정 우선순위는 오래된 값을 이기게 만들 수 있다).
5. **촘촘한 항적은 저장 경로 그대로.** focus 관측(5 s)은 기존 항적 저장(`track_point`, PK (hex, ts))으로 들어가 선택한 순간부터 5 s 간격 선이 된다.

## 대안과 기각 이유
- 브라우저가 공급자에 직접 요청: 키·약관·CORS·호출 상한을 통제할 수 없다(ADR-006 위반).
- hex 마다 개별 요청: 대상 수에 비례해 호출이 늘어 1 req/s 를 바로 넘는다. 묶음 요청은 대상 수와 무관하게 0.2 req/s.
- 핫 리전을 OpenSky bbox 로: 크레딧을 소모해 전세계 수집(ADR-009)과 충돌.

## 결과
호출량 상한(정상 사용 시 adsb.fi ≤ 0.5 req/s)과 사람이 보는 곳의 해상도(30 s / 5 s)를 맞바꾼다. 수요 임대·상태가 Redis 에 드러나 운영 화면에서 추적할 수 있다.

## 개정(2026-10-14, QA-1350) — 핫 리전 셀에 IP 당 몫(전체 상한의 절반)
- **문제**: 상한 안의 순위가 '세션 수 → 먼저 요청된 순'뿐이었다. IP 당 WS 연결 상한(5)이 핫 리전 셀 상한(6)과 거의 같아, 먼저 연결한 한 IP 가 관심 지역 밖 다섯 곳을
  줌 ≥ 7 로 보면 연결을 유지하는 동안 6 셀 중 5 셀을 쥐었다(핫 리전에는 집중 추적의 30분 같은 시간 상한도 없다). 뒤에 온 다른 IP 방문자의 두 번째 곳은 `throttled` —
  QA 2026-10-aws(공개 데모 A1)에서 재현했다. 공개 데모는 OpenSky 를 끄므로(ADR-039 결정 6) 관심 지역 밖 항공기를 보는 길이 핫 리전뿐이다.
- **결정**(사용자 2026-10-14): 핫 리전 셀에 IP 당 몫 = 전체 상한의 절반(`DemandService.MAX_HOT_CELLS_PER_IP` = 3). 다른 IP 가 원하는 셀이 상한 안에 들지 못하는 동안
  한 IP 가 3 셀을 넘겨 쥐지 못한다.
  - 순위는 그대로(세션 수 → 먼저 요청 → 키). 그 순서로 넣되 한 IP 만 원하는 셀은 그 IP 의 몫(3)이 차면 미룬다. 여러 IP 가 함께 보는 셀은 누구의 몫으로도 세지 않는다.
  - 자리가 남으면 미룬 셀을 같은 순위로 채운다 — 혼자 보는 방문자는 예전처럼 6 셀까지 쓴다. 몫을 넘겨 쥔 셀은 다른 IP 가 오면 다음 계산(≤ 1 s 모음 · 10 s 주기)에
    밀려 `throttled` 가 된다.
  - 수집기 · 임대 형식 · WS 메시지는 그대로다(밀린 세션의 상태는 전처럼 `throttled` — 계약 변경 없음).
- **근거**
  - 절반이면 두 IP 가 다투어도 반씩 나눈다 — 한 IP 가 전역 상한을 혼자 차지하지 못하게 한다(ADR-039 덧붙임 2 의 5 — IPv6 를 끈 것과 같은 목표).
  - 남는 자리는 버리지 않는다. 몫을 고정 상한으로 두면 혼자 보는 방문자 · 같은 NAT 뒤의 여러 사람이 다른 수요가 없는데도 `throttled` 를 본다.
  - 함께 보는 셀을 몫에서 빼는 까닭: 같은 칸은 호출 하나로 모두에게 간다(결정 1 — 세션끼리 공유). 그 칸 때문에 누구의 몫도 줄이지 않는다.
- **대안과 기각**
  - 순위를 '세션 수' 대신 'IP 수'로: 함께 보는 셀은 앞으로 오지만, 한 IP 혼자 쥔 셀끼리의 몫 문제는 그대로다.
  - 핫 리전에도 시간 상한(집중 추적의 30분처럼): 다시 보면 새로 시작해 막지 못하고, 보통 방문자의 화면을 끊는다.
  - IP 당 WS 연결 상한을 낮춤: 같은 NAT 뒤 방문자를 더 막는다(QA-1462).
- **남는 것**: 열쇠가 IP 라 두 IP(휴대폰 + 집)면 6 셀을 모두 쥘 수 있고, 같은 NAT 뒤 방문자들은 몫 하나를 나눈다(공개 데모는 접근 코드 뒤 — 이 정도로 둔다).
  화면 글(웹 `lib/demand.ts` 의 핫 리전 `throttled`)은 상태 값이 아니라 문구로 두 까닭을 함께 말한다(웹 후속 2026-10-14) — '핫 리전 지연 — 호출 상한 또는
  다른 방문자와 칸 나눔', title 은 공급자 호출 상한과 다른 방문자와 나눈 칸 상한(IP 당 절반)을 적고 서버가 둘을 가르지 않는다고 밝힌다.
- **회귀 막기**: api `Qa1350OneIpHoldsHotDemandCapTest` · `DemandServiceTest.chooseHot_perIpShareOnlyWhileAnotherIpWaits`.

## 개정(2026-10-18 — 관심 지역 반경도 공급자 상한 250 NM, IM-10 · 계약 v5 §G55)
- 관심 지역 반경 설정(`region_radius_nm`)은 50–250 NM 이다(예전 50–500). 관심 지역 조회도 위 adsb.fi `dist`(≤ 250 NM — 공식 문서)를 쓰는데, 반경을 자르지 않아
  400 이면 `/dist/400` 을 그대로 불렀고, 수요 계산은 그 400 NM 원 안을 `covered_by_region` 으로 보아 핫 리전을 막았다 — 250–400 NM 띠는 관심 지역 피드에도 핫
  리전에도 없었다. api 검증 · 읽기 자르기(`RegionSettings`) · 수집기(`runtime_settings`) · 웹 입력이 같은 범위를 쓰고, 넓던 때 저장한 값은 읽을 때 250 으로 자른다.
  adsb.lol `point` 의 상한은 문서를 받지 못해 확인하지 않았다(같은 범위 안이라 영향 없음).
