# ADR-014 선박(AIS) 실시간 수신: 별도 수집 컨테이너 + 스트림

**상태** 채택 · 2026-09-28

## 확인한 사실(2026-09-28 실측·문서)
- aisstream.io: `wss://stream.aisstream.io/v0/stream`, 연결 후 3 s 안에 구독(`APIKey`, `BoundingBoxes` [[lat,lon],[lat,lon]]), 구독 갱신은 연결당 초당 1회(교체), 키·IP 당 연결 3개, "Read continuously", 재전송 없음, 2026-09 부터 비압축 연결에 대역폭 제한 → permessage-deflate 사용(협상 확인).
- 실측: 동아시아(18–46N, 105–150E) 5.4 msg/s · 3.1 KiB/s · 60 s 에 303 척. 전세계 48–92 msg/s · 27–52 KiB/s · 70 s 에 6,093 척. 전세계 구독 3회 중 1회는 51 s 에 서버가 close 프레임 없이 끊음.
- AIS 값 없음 표기(USCG NAVCEN): SOG 102.3, lat 91, lon 181, COG 360, heading 511, ROT -128, ETA 월·일 0 / 시 24 / 분 60. Timestamp 61 수동 입력 · 62 추측항법 · 63 장비 비작동. 선종 코드표는 USCG AIS Guide.

## 결정
1. **별도 컨테이너 `ais`**(같은 collector 이미지, 진입점만 다름). 푸시 스트림의 폭주·재연결이 항공기 폴링 이벤트 루프를 굶기지 않게 격벽(bulkhead)을 둔다. DB 권한 없음 — Redis(`wakeline:ships`·`wakeline:ais:*`)에만 쓴다. 키는 이 컨테이너에만.
2. **수신 → 대기열 → 정리 → 10 s 배치.** 수신 태스크는 파싱 없이 원문을 제한된 대기열에 넣기만 한다(가득 차면 버리고 센다 — 위치 보고는 곧 새 값으로 대체되므로). 정리 태스크가 MMSI 별 최신 상태·정적 정보를 유지하고, 10 s 마다 바뀐 선박만 모아 `wakeline:ships` 로 XADD.
3. **끊김은 공백으로 기록.** 재연결은 1→60 s 지수 백오프+지터. 끊긴 시각·다시 붙은 시각을 `gap` 이벤트로 보내고 api 가 `ingest_gap` 에 저장, 화면 상태 바·선박 항적(점선)에 표시한다. 재전송이 없으므로 공백은 메울 수 없다.
4. **정직성.** 값 없음 표기는 null 로, Timestamp 61/62 위치는 "선박 보고 추정/수동" 표시, ETA 는 연도 없는 선원 입력값임을 표시, 크기는 A+B/C+D 보고값.
5. **화면 부하.** 줌 < 7 에서는 서버가 격자별 선박 수(`ships_grid`)만 보내고, 줌 ≥ 7 에서 뷰포트 안 선박을 스냅샷·diff 로 보낸다. 레이어를 끈 세션에는 보내지 않는다.
6. **저장.** 선박 위치는 MMSI 별 60 s 에 1점으로 줄여 일 파티션 `ship_position`(72 h 보존), 정적 정보 `ship`, 공백 `ingest_gap`.
7. **범위.** 구독 영역은 운영 설정(`ais_bboxes`). 동아시아로 시작해 서버 측 처리량·자원을 잰 뒤 전세계로 넓힌다(PERF.md 에 기록).

## 부록 A — 범위 확장 실측과 결정(2026-09-28, 계약 v3 §A)
**측정.** `make measure-ais`(ais 상태 해시·docker stats) + DB 표본 + 연결별 지연 탐침(수신 시각 − `MetaData.time_utc` 중앙값, 10 s 창). 이 기계(M1, Docker Desktop).

| 구독 | 연결 | msg/s | 지연 p50 추이 | 끊김 |
|---|---|---|---|---|
| 동아시아 `18,105,46,150` | 1 | 평균 5.3 (3.8–7.3) | 약 2 s 안정 | 0 (120 s) |

- 전세계 1연결일 때 우리 쪽 자원은 여유였다: ais CPU 평균 1.9 %(최대 2.9 %), 메모리 43 → 70 MiB(선박 24,232척 추적), api RSS 606 → 714 MiB, Redis 스트림 최대 2.5 MiB,
  대기열 드롭 0, api 소비 지연 0. `ship_position` 은 분당 2,000–5,700행(행당 약 179 B, 인덱스 포함).
- 끊김은 우리 쪽 keepalive ping timeout(1011)이었다. 컨테이너 소켓의 수신 대기열은 계속 0이었다 — 우리는 즉시 읽는데 aisstream 쪽 연결별 전달이
  뒤처져 pong 도 20 s 넘게 늦었다. 처음에는 사유가 "connection lost (no close frame)" 로 기록되어 서버 탓으로 보였고, 사유 분류를 고쳤다.

**10분 재측정(결정한 범위, 운영 중인 스택, 21:27–21:38 UTC).** 평균 61 msg/s(22–96), 지연(수신 − time_utc) 표본 60개 p50 7.9 s · p90 17.9 s · 최대 23.1 s.
지연은 2 s 와 20 s 사이를 오가며 대부분 스스로 회복했고, 한 번 20 s 를 넘어 keepalive 재연결(공백 약 2 s)이 있었다. 드롭 0, 위치 점프 격리 3,
ais CPU 평균 4.5 %(순간 45 %) · 메모리 41–67 MiB, api 637–675 MiB, Redis 38–42 MiB. ship_position 분당 1,773–2,769행(평균 약 2,160행 → 72 h 보존이면
약 930만 행, 행당 약 200 B 로 약 1.9 GB — 측정값에서 계산한 추정), 선박 30,678척 기록.
3분 탐침(2–5 s)보다 나쁘다 — 공급자 쪽 전달이 시간대에 따라 출렁인다. 선박은 20 s 에 약 100–200 m 움직이고 화면은 선박마다 관측 시각(나이)을 보이므로
이 정도 지연은 받아들이고, 넘으면 다시 연결해 지연을 끊는다.

**결정.**
1. 운영 설정 `ais_bboxes` = `-90,-180,90,0;-90,45,90,180`(0~45°E 를 뺀 전 해역). 측정한 범위 중 연결 하나가 지연을 스스로 회복하며 따라가는 가장 넓은 범위다.
   0~45°E(유럽·아프리카·중동 서부)는 그 구역만으로도 연결 하나가 따라가지 못해 뺐다. `.env` 기본값은 동아시아 그대로(설정이 비면 쓰는 값).
2. 수신 범위는 상태(`status.sources.ais.coverage`)와 지도(선박 레이어의 점선 경계·범례)로 보인다. 범위 밖에 선박이 없는 것처럼 보이지 않게 한다.
3. keepalive(ping 20 s · timeout 20 s)는 그대로 둔다. 공급자 쪽 지연이 20 s 를 넘으면 다시 연결해 지연을 없애는 대신 그 사이 데이터를 잃는다 —
   실시간 상황판에는 지연이 계속 커지는 것보다 낫다. 이때 공백은 **수신 시각** 기준으로 기록되며, 데이터 시각의 구멍은 그 순간의 지연(`lag_p50_s`)만큼 더 길 수 있다.
4. 저장 간격이 60 s 라 그보다 짧은 수신 공백은 저장점을 없애지 못한다. 그래서 항적 선은 60 s 이상 공백(또는 열린 공백)에서만 끊고,
   짧은 공백은 목록·요약으로만 보인다(계약 v3 §D).

**후속 과제.** 전 해역을 받으려면 키당 3연결 안에서 구역을 나눠야 한다(예: 아메리카+아시아·태평양 / 0~15°E / 15~45°E). 구역마다 공백을 따로 기록하고
항적 끊기를 그 구역 공백으로만 판정해야 해서 공백 표에 구역 열이 필요하다. 유럽을 둘로 나눠도 따라가는지는 아직 측정하지 않았다.

## 부록 B — 구역 나누기(2026-09-28, 계약 v4 §D)
**측정.** 한 연결(0~45°E 제외 전 해역)을 6시간 운영하니 연결 종료 51회, 공급자 쪽 지연 p50 7.9 s · p90 17.9 s(부록 A 10분 측정).
같은 범위를 두 연결(아메리카 `-90,-180,90,0` / 아시아·태평양 `-90,45,90,180`)로 동시에 10분 받으니 지연 p50 1.9 s · 1.8 s, p90 6.0 s · 4.6 s, 최대 10.1 s, 끊김 0.
**결정.** `ais_bboxes` 에 `|` 로 구역을 나눠 구역마다 연결 하나(최대 3 — 키당 연결 수). 공백은 구역(scope)별로 기록하고, 항적 끊기·만료 멈춤은 그 구역 안 선박에만 적용한다.
운영값은 위 두 구역. 세 번째 연결은 비워 둔다(측정·탐침용 여유).
**되돌리기(V8).** `DROP INDEX ingest_gap_source_scope_started_uq; ALTER TABLE ingest_gap ADD CONSTRAINT ingest_gap_source_started UNIQUE (source, started_at); ALTER TABLE ingest_gap DROP COLUMN scope; DELETE FROM flyway_schema_history WHERE version = '8';`
(scope 가 다른 같은 시각 공백이 있으면 먼저 하나만 남긴다.) 설정값에서 `|` 를 `;` 로 바꾸면 한 연결로 돌아간다.

## 부록 C — keepalive 1011 끊김: 가설 시험 · 진단 · 로그 수준(2026-09-30, 계약 v5 §G23)
**증상.** 로그 화면에 `ais shard 1 disconnected: client closed (1011 keepalive ping timeout) — reconnecting in 0.9 s` 가 08:41:56 · 08:51:01 KST 에 올랐다
(ais 컨테이너 07:09 KST 기동 뒤 2시간에 2번, 구역 1만). 재연결마다 짧은 수신 공백이 남았다(상태 바 11 s). 06:43 KST 에 두 구역이 함께 끊긴 일은 같은 분의
RainViewer ConnectTimeout 과 함께라 호스트 망 문제로 보고 이 부록에서 다루지 않는다.

**가설 시험**(`apps/collector/tests/test_ais_keepalive.py` — 127.0.0.1 가짜 서버가 초당 `RATE_HZ`(400) 프레임, ping `PING_S` 0.2 s · 시간 초과 `TIMEOUT_S` 0.8 s 로
운영 20 s · 20 s 와 같은 기제. 멈춤은 `STALL_S` = 시간 초과의 두 배(1.6 s) — 시험 기계가 바빠도 결과가 바뀌지 않게. 값은 시험 파일의 상수가 원본이다).

| 조건 | max_queue 64 | None | 4096 |
|---|---|---|---|
| 소켓을 읽는 코드(recv 를 부르는 쪽)가 `STALL_S` 멈춤, 루프는 돈다 | **1011** | 유지 | 유지 |
| 정리 태스크가 대기열을 `STALL_S` 비우지 않음(우리 구조) | 유지 — 수신 태스크가 계속 읽는다 | | |
| 이벤트 루프가 ping 이 나가 있는 동안 `STALL_S` 멈춤(CPU 작업, 타이머 콜백) — pong 은 멈춘 사이 도착, 멈춤이 끝난 다음 바퀴에 읽힘(서버는 별도 스레드) | **1011** | **1011** | |
| 같은 길이의 루프 멈춤, 소켓 콜백이 pong 을 처리한 직후 멈춤 | 유지 | | |
| 같은 CPU 작업을 스레드에서 | 유지 | | |
| 서버가 pong 을 시간 초과 + 0.3 s 늦게(데이터는 계속) | **1011** | **1011** | |
| 서버가 pong 을 시간 초과의 40 % 로 | 유지 | | |
| 서버가 600 프레임을 한꺼번에 보냄(`test_ais_diag`) | 유지 — 수신 버퍼가 상한을 넘지만 루프 지연은 작다 | | |

- 가설("소비자가 밀리면 max_queue 64 에서 읽기를 멈춰 pong 을 못 읽고 1011")의 기제는 있다. 다만 그 소비자는 **소켓을 읽는 코드**여야 한다. 우리 수신
  태스크(`client._read`)는 원문을 대기열(RawQueue — 기다리지 않음, 가득 차면 오래된 것부터 버림)에 넣기만 하므로 파싱 → ShipBook → 발행(Redis)이 밀려도
  소켓 읽기는 멈추지 않는다. websockets 수신 버퍼가 상한을 넘는 것은 한 번 읽기(asyncio 최대 256 KiB)에 프레임이 많이 든 묶음이나 루프 멈춤 뒤이고, 수신
  태스크가 곧 비운다(600 프레임 묶음: 버퍼 약 575 · 루프 지연 1 ms · 연결 유지 — `test_ais_diag`, 이 M1). 큰 버퍼는 문턱(멈춤 × 수신률)을 옮길 뿐이고
  None 은 메모리 상한이 없다.
- ping 이 나가 있는 동안 시간 초과보다 긴 루프 멈춤은 1011 을 **낼 수 있다**(버퍼 크기와 상관없다) — 늘 내지는 않는다. CPython asyncio 의 한 바퀴는 [앞 바퀴가
  넘긴 콜백] → [소켓 읽기 콜백] → [때가 된 타이머 콜백] 순서다. 멈춘 사이 pong 이 도착해 있어도, 멈춤이 끝난 뒤 pong 을 읽는 소켓 콜백과 keepalive 시간 초과
  콜백이 같은 바퀴에 들면 시간 초과가 keepalive 태스크보다 먼저 돌아 1011. 소켓 콜백이 멈춤보다 앞서(또는 멈춤과 같은 바퀴에서) pong 을 처리했으면
  keepalive 태스크가 다음 바퀴 맨 앞에서 깨어 시간 초과 콜백을 거두므로 끊기지 않는다(websockets 17.1 keepalive 는 시간 초과 콜백으로만 판정하고 경과 시간을
  다시 재지 않는다).
  운영에서 어느 쪽이 될지는 멈춘 작업의 자리와 그때 소켓에 읽을 것이 있었는지에 달려 미리 정할 수 없다. 시험은 두 순서를 각각 고정했다 — 순서를 고정하지
  않았던 이전 시험(서버와 클라이언트가 한 루프)은 8개 병렬 실행에서 32번 중 3번 결과가 바뀌었다(2026-09-30, 이 M1).
- 우리 코드가 루프 위에서 하는 일(이 M1 에서 잰 값 — 운영 기계 값이 아니다): 정리 40 µs/건(512건 묶음 20 ms), 선박 2만 척을 한 번에 꺼내 인코딩 약 0.11 s,
  평소 10 s 창 인코딩 1.7 ms. 20 s 와 거리가 멀다.
- 남는 후보는 둘이다. 공급자 쪽 연결별 전달 적체로 pong 이 늦음(VERIFICATION #17 에서 한 연결일 때 확인한 기제 — 이번에는 구역 1만 두 번), 또는 프로세스 전체가
  멈춤(호스트 · Docker VM — 두 구역이 함께 끊기기 쉽지만 위의 순서는 연결마다 달라 한 구역만 끊길 수도 있다). 지금 남은 기록으로는 가를 수 없어 다음번을 위해 잰다.

**결정.**
1. `max_queue` 64 · keepalive 20 s/20 s 는 그대로 둔다(이름 붙인 상수 `WS_MAX_QUEUE` · `PING_*`). 키우면 메모리 상한만 커지고 1011 은 줄지 않는다(위 표).
   무거운 작업을 루프 밖으로 옮기는 것도 하지 않는다 — 잰 최악이 0.1 s 대라 근거가 없다. 루프 지연 측정이 다른 것을 보이면 다시 본다.
2. **진단**(`ais/diag.py`): 이벤트 루프 지연(0.5 s 틱이 늦게 깬 만큼), websockets 수신 버퍼에 남은 프레임(구역별), 원문 대기열에 머문 시간(지금 맨 앞에서
   기다리는 원문 포함 — 정리 태스크가 멈춰도 모름이 되지 않게) · 깊이, keepalive 왕복(구역별) — 최근 60 s 최댓값. 상태 해시(`loop_lag_max_s` · `loop_stalls_total` ·
   `queue_wait_max_s` · `queue_depth_max` · `ws_queue_max` · `ping_rtt_max_s`, `shards[]` 의 `ping_rtt_max_s` · `ws_queue_max`), `GET /api/v1/ops/pipeline` 의 `ais.*`,
   운영 PIPELINE 탭, 그리고 끊김 로그 한 줄의 맥락(+ 원문 대기열 깊이/상한 · 직전 발행 창의 공급자 지연 p50)에 싣는다. 고른 값도 상태 해시에 실어(`diag_window_s` ·
   `ws_queue_limit` · `queue_limit` · `ping_timeout_s` · `loop_tick_s` · `loop_stall_s` · `loop_warn_s` · `loop_warn_every_s` · `reconnect_quick_window_s` ·
   `reconnect_warn_count` · `reconnect_warn_window_s`) api 가 그대로 옮기고 웹은 설명의 숫자를 응답에서 채운다 — 수집기가 바꾸면 화면이 따라간다. 다음 1011 을 읽는 법:
   - 루프 지연이 시간 초과 이상(한 구역만 끊겼어도) → 루프 · 프로세스 멈춤.
   - 수신 버퍼가 상한(64) 이상 → 그때 소켓 읽기가 잠시 멈춰 있었다. 그 자체는 결함이 아니다 — 루프 지연이 작으면 한꺼번에 받은 묶음(공급자 적체 해소 ·
     망이 잠깐 끊겼다 이어짐), 크면 루프 멈춤 뒤다. 버퍼 값만으로는 둘을 가르지 못한다(루프 지연과 함께 본다). 1011 과 겹칠 때만 원인 후보다.
   - keepalive 왕복 · 공급자 지연이 커지다가 끊기고 루프 지연 · 수신 버퍼는 작음 → 공급자 쪽 적체(서버의 늦은 pong).
3. **로그 수준**(`ais/reconnect.py`): 받던 연결이 끊겨 열린 공백(마지막 데이터 → 다시 받은 데이터 — AIS 수신 공백과 같은 구간)이 30 s 안에 닫히면
   INFO 와 누적 수(`reconnects_quick_total` — 운영 PIPELINE "짧은 재연결"). 창은 끊긴 순간이 아니라 공백 길이로 잰다 — idle 끊김(기본 120 s)이나 조용한
   서버처럼 끊기기 전부터 데이터가 없던 시간도 공백이라, 재연결이 빨라도 공백이 30 s 를 넘으면 WARN 이다. 같은 연결이 30분에 3번째부터 끊김 · 끊길 때 공백이
   이미 30 s 를 넘음 · 데이터 없이 끝난 연결(재연결 실패 · 핸드셰이크 거절 · 오류 프레임만) · 공백이 30 s 를 넘도록 다시 받지 못함(과 그 뒤 늦은 회복)은
   WARN(로그 화면). **공백 기록은 바꾸지 않는다** — AIS 수신 공백 목록 · `ais_gap` · 상태 해시는 로그 수준과 상관없이 모든 끊김을 싣는다.
   누적 수도 로그 수준이 아니라 공백 길이로 센다 — 되풀이 끊김(끊김 줄 WARN)이나 그 사이 데이터 없이 끝난 재연결 시도(WARN)가 있었어도 공백이 30 s 안에
   닫히면 센다(회복 줄은 INFO). 그래서 "짧은 재연결" 은 로그 화면에 없는 끊김만의 수가 아니다(리뷰 2026-09-30 — 운영 행 설명을 고쳤다).

**고른 값(잰 값이 아니다)과 이유.**
- 진단 창 60 s: keepalive 한 번(ping 간격 20 s + 시간 초과 20 s)을 덮고, 상태 쓰기(5 s)를 몇 번 놓쳐도 남는다. 5 s 칸 12개(값마다 13칸 — 메모리 상한).
- 루프 지연 틱 0.5 s(1 s 멈춤을 놓치지 않는 가장 싼 간격) · 멈춤으로 세는 지연 1 s(잰 최악 0.1 s 의 10배) · WARN 5 s(시간 초과 20 s 의 1/4, 분당 1번).
- 회복 창 30 s(공백 길이의 상한): 정상 재연결 한 번(close 3 s + 백오프 약 1 s + 연결 제한 10 s + 첫 메시지)이 20 s 안이다. 실측 keepalive 재연결 공백은 2–13 s.
- 되풀이 WARN 30분에 3번: 지금 두 구역에서 본 빈도(구역 1, 2시간에 2번)의 6배. 한 연결로 받던 때(6시간 51번 ≈ 30분에 4번, 부록 B)의 상태를 잡는다.
- 기억하는 끊김 시각 256개: 메모리 상한. 백오프(60 s 정상 연결 뒤에만 초기화) 때문에 30분에 이만큼 끊길 수 없어 수는 정확하다.
- 수신 버퍼 깊이는 websockets 17.x 의 내부 속성(`recv_messages.frames`)을 읽는다. 판을 올려 없어지면 모름(빈 값)으로 두고 한 번 경고하며, 고정한 판에서 읽히는지는
  `test_ais_diag` 가 지킨다.
